# 厳密走査の A/B 計測の回し方（#462）

厳密走査（`exactWalkMax`・`docs/spec/route-optimization.md` §3.9）を足したことで、何分多く歩けるように
なり、検索時間がどう変わったかを数字にする手順。数字は1回の検索の中で取る（§3.8 の `walkA`／`walkB`）。
別々の実行で比べると、上流（Transit API）のばらつきと区別できない。

## 何を測るか

1回の検索で次の2つを出す（`TransitRouteService` の `exactWalkMaxAb`）。

- **A**: 厳密走査の候補を混ぜずに、今のパイプラインを最後まで走らせた結果
- **B**: A の最終候補プールに厳密走査の候補を足して選び直した結果（画面に返るのはこちら）

enrich のキャッシュを共有するので、A と B は同じ上流の応答を使う。`walkB − walkA` は厳密走査の候補だけから来る。

回すのは OD 約20組（`apps/web/src/bench/od-pairs.ts`）× 昼・22時 × 予算3種で、計120検索。予算は、
OD と時間帯ごとに guidance を1本引いて出した「ふつうの乗換ルートの所要」の +20%・+50%・+100% にする。

## 前提

- `exactWalkMax` がデプロイ済みで、時刻表パックが生成されている（503 の「時刻表なし」だと `coveredBase` が全件 0 になる）
- `apps/web/.env` に開発サーバ用の値（`VITE_PROXY_BASE_URL` ほか）が入っている
- App Check のデバッグトークンを Firebase Console に登録してある（README の「開発サーバでは App Check のデバッグトークンを使います」）。
  デバッグトークンはブラウザのオリジン（ポートを含む）ごとに保存されるので、ふだんと同じポートで開く

## 手順

1. `npm --prefix apps/web run dev` を起こし、`http://localhost:<ポート>/bench.html` を開く。
   この画面は開発サーバでしか開けない（`vite build` の入力に入らない）
2. **走らせる日**を選ぶ。既定は翌日以降で最も近い平日。時刻表は平日と土休日で違うので、1回の計測の中では曜日を揃える
3. **開始**。120検索を直列に回し、検索と検索の間に3秒置く。1検索 10〜90 秒なので、全体で1〜2時間かかる。
   タブは開いたままにする（画面を離れると止まる）。**停止**を押すと、進行中の検索を終えた後に止まる
4. 終わったら **JSONL を保存**（`aruku-ab-<日付>.jsonl`）
5. **照合**。厳密走査が勝った1回乗車の経路を、OD が散るように最大10本選ぶ。乗車駅から降車駅までを
   その便の発車の5分前から Transit API に引き直し、発車が同じ分・到着が ±2 分以内の便があるかを見る。
   終わったら **照合 JSONL を保存**（`aruku-ab-verify-<日付>.jsonl`）
6. 集計する:

   ```sh
   node apps/web/scripts/ab-report.mjs aruku-ab-<日付>.jsonl aruku-ab-verify-<日付>.jsonl
   ```

   Markdown が出るので、そのまま issue に貼る

## 読み方

- **徒歩の増分**の分母は `coveredBase=1`（厳密走査が候補を1件以上返した検索）。時刻表の無い路線
  （東急・小田急・京急・西武など）が主役の検索や、厳密走査が失敗・猶予切れした検索は、差を語らないので外す
- **乗り遅れ・予算超過**は B の確定経路で数える。予算内の候補が1つも無ければ best-effort 縮退で予算外を
  返すのは今の仕様（§4）なので、0 件の対象は「厳密走査が勝った経路」の行
- **検索時間**: A は必ず全工程を走るので、厳密走査で崩壊が解けたときに浮く board-search の時間は同じ実行では
  測れない。`collapse=1 collapseB=0` の検索で A の `boardSearchMs` を引いた値を B の推定として出す。
  `exactMs` は guidance と並列なので、検索全体へ直列に乗る待ちではない
- B は「最初から厳密走査の候補を混ぜた検索」と同じではない。厳密走査の候補は、見積り勝者・先行実測・
  崩壊判定には効いていない（§3.9）

## 上流への配慮とレート制限

- Transit API は第三者の API で、レート制限が公開されていない（§3.6「並列度」）。直列に回すのはそのため
- プロキシのレート制限は IP あたり、徒歩（`googleWalkProxy`・`googleWalkMatrixProxy`）が 90 req/min、
  `exactWalkMax` が 30 req/min（`functions/src/rate-limiter.ts`）。1検索で叩く徒歩とマトリクスは合わせて十数〜30本
  （§3.8 の `walkCalls`・`matrixCalls`）で、速い検索が続くと徒歩の上限に近づく。徒歩実測が 429 で落ちても検索は止まらず、
  元の見積り（guidance／直線）が残る（§2.4 の fail-open）ので、`error` には出ない。見積りは楽観に倒れるので、
  乗り遅れ・予算超過が出たらまずこれを疑う。続くようなら `apps/web/src/bench/main.tsx` の `pauseBetweenSearchesMs` を延ばして回し直す
