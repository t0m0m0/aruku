## 0. 背景と目的

厳密走査は今、**1回乗車（徒歩→乗車→徒歩）だけ**を扱う（§3.9 の最後の項）。`bestRides` は1本の便の中で乗る駅と降りる駅の組を選ぶ作りで、乗り換えを含む経路は作れない。乗り換えが要る検索では、これまでどおり guidance とコリドーから候補を作り、崩壊すれば board-search が上流へ直列の引き直しを重ねる（§3.6）。

本書は、厳密走査を**乗換1回（徒歩→乗車→徒歩→乗車→徒歩）**まで広げる方法を書く。方針は #456 と同じで、置き換えずに候補プールへ足す。計算はサーバ側に置く（時刻表はブラウザへ渡せない・§2.1）。

## 1. 問題

記号:

- `t0` は出発時刻、`D = t0 + budgetMin × 60` は締切（どちらも運行日の0時からの秒）
- `A(s)` は出発地→駅 s の徒歩、`E(s)` は駅 s→目的地の徒歩、`F(a, b)` は駅 a→駅 b の乗換の徒歩（秒）
- `τx` は同じ駅で乗り換えるときの最小乗換時間

乗車1が便 T1（駅 b1 で乗り、a1 で降りる）、乗車2が便 T2（b2 で乗り、a2 で降りる）のとき:

- **最大化:** `A(b1) + F(a1, b2) + E(a2)`。a1 と b2 が同じ駅なら `F = 0`。乗換0回なら `A(b1) + E(a1)`（今の `bestRides` と同じ）
- **制約:**
  - `t0 + A(b1) ≤ dep(T1, b1)`
  - `arr(T1, a1) + F(a1, b2) + τx ≤ dep(T2, b2)`（`τx` を足すのは同じ駅のときだけ）
  - `arr(T2, a2) + E(a2) ≤ D`
  - 乗れない・降りられない停車（`canBoard`・`canAlight` が false）は使わない
- **同点の扱い:** §1 の選定順に合わせ、徒歩が長い → 目的地への到着が早い → 乗換が少ない、の順。今の `compareRides` の並びを、乗換回数の段だけ足して広げる

乗換の徒歩も `walkMinutes` に入る（徒歩区間の合計なので）。最大化の対象に含めるのはこのため。

**先行研究との違い:** 調べた範囲では、徒歩を**最大化**する経路探索の論文は見つからなかった（徒歩を基準にする論文は、どれも最小化）。以下は、到着時刻を求める後ろ向きプロファイルの**形**を借り、運ぶ値を「この先で稼げる徒歩」に替えたもの。確立した手法ではないので、正しさはテストで押さえる（§5）。

## 2. 借りる考え方

- **後ろ向きプロファイル（CSA）:** 接続を出発時刻の降順に1回走査し、各駅の「プロファイル」を (発車時刻, 値) の組の列として持つ。組は発車時刻と値の両方で整列している。CSA は、最早到着の後ろ向きプロファイル（目的地 t への、t 以外の全駅からのプロファイル）をこれで求める。
- **rRAPTOR:** 出発時刻を遅い順から早い順に並べ、ラベルを引き継ぎながら回す。遅く出る経路が、早く出る経路を支配する。
- **後ろ向きの等時線:** 目的地から後ろ向きに探索し、各地点の「間に合う最も遅い出発時刻」を持つ。時刻表の区間と徒歩の区間を、1つの探索の中で扱う。
- **Early Pruning:** 乗換の辺を所要時間の短い順に並べておき、改善の余地が無くなった時点で残りを打ち切る。

aruku では、「遅く発車するほど選択肢が減る」という単調性だけを使う。駅 s から時刻 τ 以降に乗ったとき稼げる徒歩の最大値は、τ について単調に減る。だから駅ごとの発車列の後ろから累積の最大値を取っておけば、二分探索1回で引ける。

## 3. 計算手順

時刻表パックの今の配列（`tripStart`・`callStop`・`callArr`・`callDep`・`departureStart`・`departureAt` など）をそのまま使う。新しく要るのは、乗換の近傍の表（§3.3）と、検索ごとの作業配列だけ。

### 3.1 最後の乗車の値 `V0`

便の停車 c に乗っている状態から、後ろのどこかで降りて目的地まで歩いたときに稼げる徒歩の最大値。

- `V0(c) = max { E(stop_j) : j は c より後ろの停車, canAlight, stop_j ≠ stop_c, arr_j + E(stop_j) ≤ D }`。無ければ −∞
- `stop_j ≠ stop_c` は、乗った駅と同じ駅では降りないという条件（今の `bestRides` と同じ。同じ駅に戻ってくる便があるため）。後から捨てるのでは足りない: B → C → B と回る便で `E(B) > E(C)` だと、累積の最大値1つは2回目の B を残して C を捨てるので、最初の B から乗ったときの正しい答え（C で降りる）が消える
- そこで便ごとに後ろから1回なめるとき、累積の最大値を1つでなく、**降車駅が互いに違う上位2つ**（値・降車駅・目的地への到着時刻）で運ぶ。`V0(c)` は1位の降車駅が `stop_c` でなければ1位、そうなら2位。除く駅は1つだけなので2つで足りる。新しい停車を足すとき、同じ駅の項がすでに上位にあれば、それを更新して重複させない
- 同点のときのために、目的地への到着時刻も一緒に持つ
- 対象は、`[t0, D]` に発車がある便だけでよい（今の `boardableTrips` と同じ絞り方）

### 3.2 駅ごとのプロファイル `P0`

駅 s の発車列（`departureStart[s]` 〜 `departureStart[s+1]`。発車時刻の昇順）の各発車 i について、その便のその位置から乗ったときの値を `V0` で引く。それを列の**後ろから累積の最大値**にしたものが `P0(s)[i]`。

- `best0(s, τ) = P0(s)[lowerBound(departureAt, τ)]`。駅 s に時刻 τ に着いたあと、乗換0回で稼げる徒歩の最大値
- CSA のプロファイル（(発車時刻, 値) の組の列）を、今の発車列に合わせた配列として持つ形。新しい並べ替えは要らない

### 3.3 最初の乗車の値 `V1`

便 T1 の停車 c に乗っている状態から、後ろの停車 j で降り、そのまま目的地へ歩くか、乗り換えるか。

- `W(j) = max( 終わる: E(stop_j) [arr_j + E(stop_j) ≤ D のとき] , 乗り換える: max over s' ∈ N(stop_j) of F(stop_j, s') + best0(s', arr_j + F'(stop_j, s')) )`
- `F'(a, s') = F(a, s') + (a と s' が同じ駅なら τx、違う駅なら 0)`。2本目を探し始める時刻には `F'` を、稼げる徒歩には `F` を使う（`τx` は待ちであって徒歩ではない）。§1 の制約どおり、別の駅へ歩いて乗り換えるときは `τx` を課さない
- `V1(c) = max { W(j) : j は c より後ろの停車, canAlight, stop_j ≠ stop_c }`。乗車駅の除外は §3.1 と同じで、求め方も同じ（降車駅が互いに違う上位2つを後ろから運ぶ）
- `N(a)` は駅 a からの乗換の近傍で、`F` の短い順に並べておく（クエリに依らないのでパックを作るときに作れる）。`arr_j + F > D` になったら、それより遠い近傍は全部間に合わないので打ち切る（Early Pruning と同じ発想）。打ち切りの判定は `F'` でなく `F` で行う。同じ駅の項は `F'` だけが大きいので、先頭で間に合わなくても後ろの近傍は間に合い得る
- 同じ駅の乗換は `N(a)` の先頭に `F = 0` で入れる。JR の `stop_id` は路線ごとに分かれているので、駅名と座標で同じ駅をまとめる必要がある（§8）
- そのあと駅ごとの発車列で `P1` を作る（§3.2 と同じ手順）

### 3.4 答え

徒歩の最大値は `max over 駅 b of A(b) + best1(b, t0 + A(b))`。`best1` は `P1` を二分探索で引いたもの。駅ごとに1回引くだけで済む。

ただし累積の最大値は、各状態で最良の続き1つ（と §3.1 の2位）しか残さないので、そこから組み立て直せるのは最良の1本だけになる。たとえば乗れる駅が1つしかなければ、降車や乗換の組が5通りあっても候補は1本しか出ない。今の `bestRides` は上位 k 本を返し、enrich が1位を落としたときの次善もそこから来る（§4 #254）。そのため上位 k 本は、プロファイルから復元せずに**分枝限定で列挙する**:

- 枝は、乗車駅 b1 → 発車（便 T1）→ 降車 a1 → (終わる | 乗換先 s' → 発車（便 T2）→ 降車 a2) の順に降りる
- 各枝の上界は、**ここまでに積み上げた徒歩**に、その状態から先で稼げる徒歩の最大値を足したもの（乗車駅では `A(b1) + best1`、便 T1 に乗った状態では `A(b1) + V1`、乗換先 s' では `A(b1) + F(a1, s') + best0`、便 T2 に乗った状態では `A(b1) + F(a1, b2) + V0`）。比べる相手の k 番目は経路全体の徒歩なので、先の値だけで比べると、`A(b1) = 600`・`V1 = 600` の枝を閾値 900 で切ってしまう（中に 1200 の経路がある）。先の値はどれも厳密な最大値なので、上界として正しく、しかも緩くない
- 手元に、まとめた単位（下記）ごとに最良の1本を持ち、その上位 k 本を保つ。上界が k 番目の徒歩より**小さい**枝は切る。切った枝の中に上位 k 本へ入る経路は無い。徒歩が k 番目と等しい枝は切らない（到着の早さで勝ち得る・§1 の同点の扱い）
- 子の枝は上界の大きい順に降りる。良い経路から先に見つかるので k 番目が早く上がり、切れる枝が増える
- まとめる単位は、今の `bestRides` と同じく、乗換0回なら（乗車駅, 降車駅）、乗換1回なら（b1, a1, b2, a2）。同じ単位の中では §1 の同点の扱いで1本を残す
- 1位だけで足りる用途（計測など）では、列挙せずに上の `max` だけを引く。そのため累積の最大値の配列には「どの停車から来たか」の添字も持たせる（b1・T1・a1・b2・T2・a2 を復元する）
- 列挙の手間は、上界がどれだけ早く k 番目を下回るかで決まり、最悪は総当たりと同じになる。§7 の計測で、計算時間の最大を見る

### 3.5 計算量の見込み（未計測）

`V0`・`P0` は停車の数に比例する。`V1` は「停車 × 近傍の数」で、近傍の数がそのまま効く。徒歩を自由に扱う研究では、推移閉包を取る前に乗換を 20 分に限るだけでもグラフが実用には大きすぎた、という報告がある（ULTRA の論文が引く Wagner・Zündorf 2017）。aruku は乗換が1回までなので推移閉包は要らない（1回の乗換で1本の近傍の辺だけを見る）。ただし、近傍の半径（`F` の上限）は計測で決める（§7）。

## 4. 徒歩の実測（マトリクス 25 要素の上限）

今は、直線の徒歩（実際の徒歩の下限）で1パス目を回して実測する駅を選び、乗車側・降車側 12 駅ずつ（合計 24 要素）を Google マトリクスで測ってから、2パス目を回す（§2.1）。

- **`A`・`E`:** 今と同じ2パスで測る。`pickStopsToMeasure` は、乗車側を最初の乗車の上位から、降車側を最後の乗車の上位から拾うように広げる
- **`F`（乗換の徒歩）:** 1検索で測れる要素数に入らないので、**走査は直線の値で行う**。直線は下限なので、選ぶ段階では楽観側に倒れる。これは §1.1 の「見積りは楽観側に倒す」と同じ向きで、正しさは次の2つが受け持つ:
  - 採用前の enrich（`enrichWalkGeometry`）は、polyline が2点以上ある徒歩区間を全部 Google で実測する。乗換の徒歩区間にも乗換駅の2点の polyline を持たせる
  - `firstMissedTransit` は全ての電車区間を、累積の時間で順に判定する。乗換の徒歩が伸びて2本目に乗り遅れれば、ここで分かって候補から落ち、次善が選ばれる（§4 #254）
- **気になる点:** 乗換の徒歩が直線より大きく伸びる組（川・線路をまたぐなど）ばかりが上位に並ぶと、上位 k 本が enrich でまとめて落ち、厳密走査が空振りする。#462 の計測で「乗換つき候補が enrich で落ちた割合」を見て、多ければ次のどちらかを足す:
  - (a) 上位 k 本を、乗換の組（a1, b2）が互いに違うものから選ぶ
  - (b) `findExactWalkMax` の中で、上位の候補の乗換の徒歩だけを測り直し（3回目の往復）、測った値で選び直す

## 5. テスト（What）

純粋関数 `exact-scan.ts` の側で、TDD で先に書く:

- 乗換0回の答えは、今の `bestRides` と一致する（回帰。上位 k 本の並びまで一致する）
- 乗換1回のほうが徒歩が長いときは、乗換1回の経路を返す
- 乗換の徒歩のあとで2本目が発車済みなら、その乗換は使わない
- 同じ駅の乗換は徒歩0とし、最小乗換時間を守る
- 別の駅へ歩いて乗り換えるときは、最小乗換時間を課さない（到着＋乗換の徒歩ちょうどに発車する便に乗れる）
- 同じ駅に戻ってくる便（B → C → B）で、B から乗ったときに C で降りる経路を返す（2回目の B の値が大きくても）
- 乗れる駅が1つだけでも、降車や乗換の組が違う候補を上位 k 本まで返す
- 出発側の徒歩が長く、先で稼げる徒歩だけでは k 番目に届かない枝でも、合計で届くなら上位 k 本に入る
- （エンジン側）別の駅への乗換の徒歩は、見積りが0分でも候補の区間に残る
- 乗れない・降りられない停車（通過駅・片側だけの乗降禁止）では乗り換えない
- 目的地への到着が締切ちょうどの経路は使える
- 徒歩が同じなら目的地への到着が早いほう、それも同じなら乗換が少ないほうを返す
- **小さな乱数の時刻表で、全ての組を総当たりした上位 k 本と一致する**（先行研究が無いので、正しさは総当たりとの照合で押さえる。1位だけでなく上位 k 本を照合するので、分枝限定の切りすぎもここで分かる）

## 6. 応答とエンジン側・仕様書への影響

- **応答は足すだけにする:** `exactWalkMax` の応答の `candidates`（1回乗車）は形を変えず、乗換つきは新しい配列（例: `transferCandidates`）に入れる。Functions と Web（Pages）は別々にデプロイされるので、古い Web が乗換つきの候補を1回乗車として読み違えないようにする
- **エンジン:** `exactWalkCandidates` を `徒歩 → 電車 → 徒歩 → 電車 → 徒歩` まで組めるように広げる。乗換の徒歩区間は polyline に乗換駅の2点を持つ（enrich に測らせるため）。0分の徒歩区間を落とす今の決まり（`exactWalkCandidates` の `minutes > 0`）は、出発側・目的地側と同じ駅の乗換にだけ当てる。**別の駅への乗換は、直線の見積りが0分に丸まっても区間を残す**。enrich が測るのは `segments` に在る徒歩区間だけなので、落とすと実測されず、`firstMissedTransit` は2本の電車を直結とみなして乗れない接続を通してしまう（§4 の安全網が効かない）
- **仕様書（実装と同じコミットで直す）:** §3.9 の「対象は1回乗車だけ」・§2.1 の `exactWalkMax` の行・§3.2 の候補の種別4・§3.8 の計測項目（乗換つき候補の数と、enrich で落ちた数）

## 7. 計測と完了条件

- **速さ:** #456 の試作と同じ9フィードで、1検索の計算時間の p50・p95・最大を測る（1回乗車は p50 0.048 ms・p95 0.30 ms・最大 2 ms）。近傍の半径を振って、計算時間と「乗換つき候補が勝った割合」の関係を見てから半径を決める
- **効き目:** #462 の A/B（同じ実行の中で A＝今のパイプライン、B＝A の最終プール＋厳密走査で選び直す）に、乗換つきの候補を足した B' を加え、`walkB'` と `walkB` の差・`exactWon` の変化・検索時間を比べる
