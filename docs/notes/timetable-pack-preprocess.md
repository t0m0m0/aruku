# 時刻表パックの前処理の計測と改善（#487）

`exactWalkMax` は、インスタンスの初回・6時間ごとの読み直し・運行日の切替のときに、時刻表パックの読み込み
（`functions/src/timetable-pack/load.ts`・`decode.ts`）と運行日の組み立て（`day.ts`）を要求の中で走らせる。
ここでは、その前処理をどう測り、何を採用して何を見送ったかを記録する。

## 測り方

- **本番:** `timetable_pack_load`（`readMs`・`gunzipMs`・`parseMs`）、`timetable_day_compile`
  （`extractMs`・`compileMs`・`neighborsMs`・`heapUsedMB`）、`exact_walk_max.dayMs`。項目の意味は
  [observability.md](../ops/observability.md) の表を正本とする。
- **手元:** `npm run pack:bench -- --dir .odpt/bench`（`functions/` で実行）。パックは `pack:local` で作る。
  初回・同じ日の2回目・日付の切替・6時間後の読み直し・同時の初回要求（8本）を、1回ごとに新しいプロセスで測り、
  中央値と p95 を出す。Storage の読込はディスクの読込に置き換わるので、`readMs` は本番の代わりにならない。
  あわせて、組み立てた時刻表が「パックを1つずつ `timetableForDate` で切り出して連結し `compileTimetable`・
  `transferNeighbors` に掛けたもの」と一致すること、駅ごとの発車の並びと過不足を確かめる。

## 結果

### 変更前の本番（2026-10-10〜11-09、n は少ない）

| 条件 | 値 |
| --- | --- |
| パックの読み込み `loadMs` | challenge 1.1〜1.9 秒・permanent 0.5〜0.8 秒（3回） |
| 運行日の組み立て（変更前の `compileMs`＝今の `totalMs`） | 0.6〜0.9 秒（3回） |
| `exact_walk_max.dayMs`（初回） | 中央値 1.7 秒・p95 2.8 秒（7回） |
| `exact_walk_max.dayMs`（温まった後） | 中央値 0 ms・p95 1 ms（84回） |
| ハンドラ全体（`dayMs`＋`matrixMs`＋`scanMs`） | 中央値 0.16 秒・p95 1.9 秒・最大 3.0 秒（91回） |

ハンドラの中では、最大でもエンジンの猶予 `exactWalkMaxGrace`（5秒）に収まっていた。ただしコールドスタート
そのものと、App Check・レート制限・通信の時間は含まない。

### 手元（Node 22・M 系 Mac・実パック 2.0MB gzip・運行日 20261110・15回の中央値/p95、単位 ms）

| 条件 | 変更前 | 変更後 |
| --- | --- | --- |
| 初回（読み込み＋組み立て） | 229 / 260 | 161 / 178 |
| 　うち組み立て（抽出・compile・近傍） | 117（64・46・8） | 54（28・19・8） |
| 日付の切替（組み立てだけ） | 108 / 138 | 39 / 42 |

読み込み（解凍 約34ms＋JSON の解析 約72ms）は変えていない。本番での効果は、デプロイ後に上の本番の項目で確かめる。

## 採用したもの

1. **運行日の時刻表を、停車のオブジェクトを経ずに列の配列へ直接書く。** 変更前は、`timetableForDate` が停車ごとに
   オブジェクトを作り、2つのパックの連結でもう一度作り直していた（1日ぶん約41万停車）。
2. **駅ごとの発車の索引を型付き配列で作る。** 便・停車順に書き込み、並べ替えが要る区間だけを数値の並べ替え1回で
   並べる（`compileColumns`）。

どちらも出力は変わらない。テストと `pack:bench` の確認で一致を確かめた。

## 見送ったもの

- **乗換の近傍を読み込みごとに1回だけ作る。** 近傍は駅の座標と駅のキーだけで決まり、運行日に依らないので
  使い回せる。ただし1回 7〜8ms で、日付の切替の 39ms のうち2割に満たない。キャッシュの持ち主を1つ増やすほどの
  効果がない。
- **非同期の解凍（`zlib.gunzip`）。** 解凍を別スレッドへ逃がしても、縮むのは手元で高々 34ms。その倍の時間が
  かかる JSON の解析は同期のまま残るので、初回の待ちはほとんど変わらない。
- **JSON の解析を減らす（列ごとのバイナリ形式など）。** 読み込みの残りの大半を占めるが、パックの形式
  （`PACK_FORMAT_VERSION`）と作る側（`refresh.ts`）の変更になり、本件の範囲を超える。
- **パックの更新時に運行日の時刻表を作っておく。** 作る側の変更が大きい。運行日が日ごとに替わるうえ、0時の前後で
  2日分が要る。
- **要求の外で前もって組み立てる。** Cloud Functions は要求の外で CPU を絞るので、終わらないまま残る
  （`load.ts` の `RELOAD_AFTER_MS` のコメント）。
