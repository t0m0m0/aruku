# ルート最適化 用語集

[route-optimization.md](route-optimization.md) が仕様の正本。本書は**そこで使われる語の定義を1枚に集めたもの**で、規範ではなく索引。定義が食い違ったら正本が優先する。

正本は「なぜそうなっているか」を厚く書く方針のため、用語の定義が本文の各所に散っている。初見で追えるようにするのが本書の目的。

---

## 1. 目的関数まわり

このアプリは「**制限時間内で最大限歩く**」ためのもので、電車は歩きでは間に合わない区間を補う手段。**速さを競うアプリではない**——時間が余るのは失敗である。この前提が「崩壊」（§4）という強い語に繋がる。

| 用語 | 定義 |
|---|---|
| **予算（budget）** | ユーザーが指定した出発〜到着の持ち時間（分）。`budgetMinutes(departure, arrival)` |
| **余り（slack）** | `予算 − 実到着`。余っている＝もっと歩けたはず、を意味する劣化の指標 |
| **目的関数** | 到着 ≤ 予算 を**制約**に、`walkMinutes`（徒歩の分数）を**最大化**する |
| **選定順** | 徒歩最大 → 実到着が早い → 乗換が少ない。確定経路は1本（代替案提示は #327 で撤去） |

`walkKm` ではなく `walkMinutes` を正とする（正本 §1・限界1）。

## 2. 候補の種別

| 用語 | 定義 | 発着時刻 |
|---|---|---|
| **全徒歩** | 出発地→目的地を歩き通す候補。常にプールに入る | — |
| **標準乗換** | `/guidance/plan` が返した door-to-door 経路そのまま | **実ダイヤを持つ** |
| **ハイブリッド** | 基準経路の**途中駅で乗降**し、その分を歩く候補。徒歩最大化の主役 | **持たない**（§3 コリドー由来） |

全徒歩が常に候補に残るのは、transit を含まないため**絶対に乗り遅れない**から。乗り遅れ除外のループが必ず収束することの根拠になっている（正本 §4 #254）。

---

## 3. 中核の仕掛け

### コリドー（corridor）

上流 API は**途中停車駅を返さない**（leg は乗車駅と降車駅しか持たない）。代替として電車区間の **polyline 座標**を順序付きの点列として使う。これをコリドーと呼び、最大 `_maxCorridorStops`（60）点へ間引く。

「駅」ではなく「線路上の座標」だが、そこから引き直すと API が最寄り駅にスナップして実在の便を返す。この性質の上に徒歩最大化が乗っている。

### フロンティア（frontier）

コリドー全点を実測すると高コストなので、**直線距離**で「乗車側は origin から予算内」「降車側は goal まで予算内」の点に絞り、さらに片側 `_maxMatrixSideStations`（10）点へ均等間引きする。

直線は実際の徒歩の**下限**なので、直線ですら予算外なら確実に予算外＝落として安全。逆に道なり迂回の割増は**掛けない**（掛けると徒歩最大の正当な候補を誤って落とす）。

### measure-first

| 用語 | 定義 |
|---|---|
| **見積り** | 直線距離や API の概算から得た徒歩時間。安いが**楽観に倒れる**（実機で -36分・25%） |
| **実測 / enrich** | Google Routes で実街路を引いた値。高いが正しい |
| **measure-first** | 「見積りで絞り、実測で決める」方針。見積りは候補を**落とす方向にしか**使わない |

旧方式は「実測して超過したら迂回率を学習して選び直す」8回ループ（正本 §3.4・撤廃済み）。

### t1 / t2

- **t1** — 前半徒歩。`origin → 乗車地点`
- **t2** — その先。`乗車地点 → goal`

到着 = t1 + t2 で、`t2 ≥ 0` なので **t1 単独で予算外の点は確実に予算外**。この安全上界が乗車駅探索の刈り込み（`walkFeasiblePrefixCount`）の根拠。

## 4. 崩壊（collapse）

**このリポジトリ固有の語で、バグの名前。** 徒歩最大化が機能せず「**短い徒歩＋大きな余り**」へ落ちた状態を指す（実機例: 蒲田→上野公園で徒歩3分・余り137分）。

普通のルート検索なら「速く着いた」＝正常だが、このアプリでは**失敗**なので専用の検出器と救済策を持つ。

判定（`_isCollapse`）は次の**両方**を満たすとき:

1. 確定経路の徒歩が、予算内標準乗換の最大徒歩を **`_collapseWalkMarginMin`（10分）以下しか上回らない**
2. 余りが **予算の `_collapseSlackRatio`（40%）以上、または `_collapseSlackMinutes`（20分）以上**

②が相対と絶対の or なのは、予算が大きいとき（例: 147分）に相対閾値へ届かず、絶対的には大きな余りを見逃していたため。

判定は **enrich 前の見積り基準**で行う（実測後の徒歩は実街路で膨らみ、標準乗換の見積り徒歩と測定基準がずれるため）。

---

## 5. 乗車駅探索（board-search）

崩壊時**だけ**走る救済策。「もっと手前の駅から乗れば、その分歩ける」を探す。コリドー上の点 X から `plan(X→goal)` を引き直し、「**到着が予算内である最も遠い X**」を求める。

| 用語 | 定義 |
|---|---|
| **probe** | 1点 X の評価（徒歩実測1本＋引き直し1本） |
| **ラウンド** | 探索の1段。1ラウンドで `fanout` 点を**同時に**評価する |
| **fanout** | 1ラウンドの同時発行数。`_boardSearchFanout`（5）に固定 |
| **境界（best）** | **評価済みのうち予算内だった最遠 index**。探索の戻り値そのものではない |
| **scanCount** | 実際に走査した点数（t1 で刈った後の範囲） |

**ラウンド間は直列**（前の結果で次の撃ち先が決まる）。壁時計 ＝ ラウンド数 × 最遅1 probe。

fanout を上げられないのは上流の**未知のレート制限**のため。429 は現状「予算外」と誤認され、**境界を実測ではなくレート制限が決める**（→ 徒歩が静かに縮む・#333）。

境界1本ではなく**評価済みの予算内候補を全部**プールへ返す。到着は実街路で非単調になり得る（後方の駅の方が origin に近いことがある）ため、境界＝徒歩最大とは限らないから。

## 6. 縮退（degradation）— 2つの意味がある

**同じ語が2つの異なるものに使われている。** 読むときは区別すること。

### (a) best-effort 縮退 — 選定の縮退（設計された代替戦略）

**予算内候補が1つも残らなかったとき**に目的関数を切り替え、「**実際に乗れる範囲で実到着が最早**」の候補を選ぶ。UI の「最短を表示」バナーに対応する。実装は `_bestEffortResolved` / `giveUp`。

最長（全徒歩）ではなく最早を選ぶこと、「今夜は乗れない」便を後回しにすること、実測で乗り遅れる経路は縮退先にも出さないことが不変条件（正本 §1・§4 #121②・#254）。

### (b) フォールバックとしての縮退 — 部品の劣化

上流が失敗したとき、より安価で不正確な手段へ落ちること。

- 徒歩実測が失敗 → **直線推定へ縮退**
- 引き直しが失敗 → `null` → 「予算外」扱いへ縮退
- matrix が失敗 → 直線推定のみで刈る

(a) は意図された戦略、(b) は障害時の劣化。**(b) は静かに品質を下げる**ので、`probeFailed` のような印を残して集計から除く設計になっている。

## 7. 検証まわり

| 用語 | 定義 |
|---|---|
| **幻便・幽霊バス** | 実在しない便。ハイブリッドは発車時刻を持たないため、深夜に「待ち0分で乗車」と計算され走っていない電車が予算内へ化ける（実機 02:41） |
| **approach A** | 採用候補の時刻なし transit 区間を、実 `boardAt` で引き直して実発着時刻を当てる検証（`_resolveBoardingTimes`） |
| **unverified** | 引き直しても実発車時刻を確認できなかった transit 区間。**確定させない** |
| **乗り遅れ（`firstMissedTransit`）** | 実測徒歩で駅に着いたとき既に発車済み。`arrivalMinutes` は「待ち0で乗れた」と楽観近似するため、**必ず併用**しないと乗れない経路を提示する |
| **逆戻りフィルタ** | 進行方向に対し大きく後退する経路の除外。判定は polyline の全頂点ではなく端点＋均等サンプリング点で行う |
| **last-resort（バス）** | バスは電車と同格ではなく「電車で予算内に届かないときの最後の手段」。best-effort が**なお予算外か乗り遅れる**ときだけ高々1回引く |

### fail-open / fail-closed

失敗したときに**嘘をつく方向か、安全側に倒れるか**。

| 呼び出し | 失敗の向き | 締切 |
|---|---|---|
| Transit 引き直し | **fail-closed**（候補が除外され確証ある候補へ縮退） | **適用する** |
| 徒歩実測（Google プロキシ） | **fail-open**（楽観的な見積りが残り予算超過を「予算内」と偽る） | **適用しない** |

**実測は探索の「改善」ではなく確定経路の「検証」**であり、締切より優先する。切ると答えが劣化するのではなく**嘘になる**（再現済み: 実際46分の全徒歩を35分予算内として「23分」で確定）。

## 8. 時間の制御（3層）

| 層 | 値 | 役割 |
|---|---|---|
| Transit 1本 | 35秒（`transitRequestTimeout`） | ハング検出 |
| 徒歩プロキシ1本 | 15秒（`proxyRequestTimeout`） | ハング検出 |
| **検索の締切** | **120秒**（`searchDeadlineBudget`） | 体感の保証 |

**締切（deadline）** は失敗ではなく**打ち切り**。必須なのは初回照会1本だけで、それ以降は徒歩最大化のための**改善**なので、改善側だけをゲートできる。

**truncated** — 締切で打ち切られた印。打ち切られた境界は本来より手前になり得るので、境界位置の分布からは除く。

> **締切に張り付いた検索では、段数を削っても `totalMs` は縮まない。** 空いた予算を board-search が探索に使うため、利得は速度ではなく**探索の深さ**に化ける（2026-07-28 実測）。

## 9. 計測の用語（#309 系）

| 用語 | 定義 |
|---|---|
| **臨界パス** | 並列に走る中で全体の壁時計を決めている最長の連鎖 |
| **段数 / 幅** | 段数＝直列に積んだ上流呼び出しの数、幅＝1段で同時に投げる本数。**幅を増やしても床は下がらず、段数だけが効く** |
| **パス（pass）** | 候補群を1回の `Future.wait` でまとめて実測する単位。パス間は直列、パス内は並列 |
| **単一測定口** | 実測を1箇所へ集約する設計（`_measureCandidate`）。**二重計測を防ぐためのもので、全経路がそこを通る保証ではない**（best-effort 縮退は通らない） |
| **反実仮想** | 同じ実行の中で「もし直列を解いていたら」を同時に計算する測り方。別 run の A/B では上流のばらつきと区別できないため |

計測フィールドの一覧と読み方は正本 §3.8。

## 10. 全体の流れ

```
① /guidance/plan を1回引く（必須・削れない）
        ↓
② 候補を作る
   ・標準乗換（door-to-door そのまま）
   ・全徒歩
   ・ハイブリッド ← コリドーの途中駅で乗降し、アクセス徒歩を matrix で一括実測
        ↓
③ 見積りで予算内の候補を並べる（短リスト・最大13件）
        ↓
④ 上から実測（enrich）して検証
   ・徒歩を実街路で測り直す
   ・時刻なし区間は引き直して実発車時刻を当てる（approach A）
   ・予算超過 / 乗り遅れ / 幻便 は棄却して次へ
        ↓
   ├─ 生き残りあり → 確定（徒歩最大の生存者）
   └─ 全滅 → best-effort 縮退（実到着最早へ）
              └─ なお予算外 → バス last-resort → プールへ足して選び直し
        ↓
⑤ 崩壊判定（徒歩が伸びていないのに予算が余っていないか）
        ↓
   崩壊 → 乗車駅探索で「もっと手前から乗る」候補を追加 → ④へ戻る
        ↓
⑥ 駅名を復元して確定
```

設計の背骨は「**見積りで絞り、実測で決める**」。見積りは楽観に倒れるので候補を落とす方向にしか使わず、確定は必ず実測を通す。そのうえで「予算が余っているのに歩けていない」状態（崩壊）を検出したら探索をやり直す、という二段構え。

## 11. なぜこれだけの語彙が要るのか

**難しさのほぼ全部が「上流 API が途中停車駅を返さない」という1点から派生している。**

```
途中駅が取れない
  → コリドー（座標で代用）
      → ハイブリッドが発車時刻を持たない
          → 幻便の検証（approach A）が必要
              → 引き直しで上流1本ぶんの段が増える
                  → 直列段数が壁時計を決める
```

途中駅と時刻が取れるデータ源が手に入れば、この連鎖の大半は消える。データ源の制約（正本 §2.2）が設計を規定しているという構図を押さえておくと、個々の判断の理由が追いやすい。
